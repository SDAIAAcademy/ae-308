The escape

The check read the name of the path, not where it leads

# the first policy
def allowed_first(path, work):
    p = os.path.abspath(path)
    return p.startswith(
        os.path.abspath(work) + os.sep)

# the path as written
#   work/ref/importers.csv
# the path it resolves to
#   data/importers.csv
  • ref is a link inside the work folder, left by an earlier job
  • The name starts with the work folder, so the check passes
  • The operating system follows the link to the data folder
  • The code never left /work, by name
What goes wrong. Any check on a path as text can be walked around with a link, .., or a second name for the same file.

The lab creates a real link (a junction on Windows) and prints both paths. This is the classic path traversal, decades older than language models; what is new is that the code that exploits it is written on demand by a model that read an invoice.

The fix

Resolve the path, then check it, and check the same object you open

def allowed(path, work):
    p = os.path.realpath(path)   # follows links
    return p.startswith(
        os.path.realpath(work) + os.sep)
SnippetResolved
Benign duty2250.0
Read importers, post themdenied
Overwrite a tariff ratedenied
Read importers through a linkdenied
Exact zeros. These denials do not depend on a model. They hold in every trial, and 100% of the 50 benign tasks still pass.

Real output. The slide shows the rule for the work folder; the lab's function also takes the tariff folder and a write flag. Mention the remaining gap between check and use: a link swapped after the check. A container closes it by not mounting the data folder at all, which is why the mount table comes before the path check.

Session 3

Delegated authorisation

  • Explain token passthrough and the confused deputy
  • Exchange a user token for an audience-bound short-lived token
  • Audit every tool call's token and test the deputy
03

Session 3: authority. Until now the question was what the agent can reach. Now it is in whose name each call is made. This session carries outcome 4 alone, so take the full time.

As found

One key opens both servers, and it is written in the system prompt

  • FANAR-KEY-... is accepted by the case server and the comms server
  • With it: read any importer, write any case, release any hold
  • The case server knows one thing about the caller: "shared-key"
  • The key is in the system prompt, so A-24 can print it

Three problems in one

No audience: it works everywhere. No scope: it allows everything. No expiry: it works until someone rotates it by hand.

Real output of Lab 3.3's first step: what the case server knows about the caller is {'sub': 'shared-key', 'aud': 'any'}. OWASP ASI03, identity and privilege abuse; LLM08 for the key in the prompt.

The confused deputy

The comms server uses its own authority for whoever asks

A callerallowed to send email, asks for the summary of any case
→
The comms serverasks the case server, with the shared key
→
The case serversees a valid key and returns the record
→
The comms serveremails it to the address the caller named
What goes wrong. Each server did what it was built to do. Nothing bound the request to the rights of the one who made it.

This is send_case_summary, one of the three actions no benign task uses. The problem is far older than language models; the protocol's security guidance lists it together with token passthrough. Sources: Model Context Protocol specification, security best practices.

The tempting fix

Passing the officer's own token to every server replaces one wide key with another

Shared keyToken passthroughExchanged token
Whose authorityNobody'sThe officer's, all of itThe officer's, for this call
Works atEvery serverEvery server that trusts the providerOne audience
AllowsEverythingEverything the officer may doOne scope, one case
LivesUntil rotatedThe officer's sessionTwo minutes

The protocol's authorisation text forbids passthrough: a server must not accept or forward tokens that were not issued for it. The third column is what the lab builds. Sources: Model Context Protocol specification, authorization; RFC 8707.

Token exchange

The agent trades the officer's token for a small one, per tool call

{
  "iss": "https://id.fanar.example",
  "sub": "officer.jihad",
  "act": {"sub": "mukhallis"},
  "aud": "case-server",
  "scope": "case:write",
  "case": "MSG-0011",
  "exp": "iat + 120 seconds"
}
  • sub: in whose name. act: who is acting
  • aud: the one server that may accept it
  • scope: the one thing it allows
  • case: the case the officer opened
  • The provider's policy decides what the agent may ask for

A real token from the lab, with the two timestamps written as their difference. RFC 8693 defines the exchange and the act claim. The lab's identity provider runs in process and signs real tokens; in production this is Keycloak or the organisation's own provider, and the labs' README says so. Sources: RFC 8693; Keycloak, token exchange.

The servers' side

A token is only as narrow as the checks the server makes

  1. Signature and issuer: is it from our provider?
  2. Audience: is it for me?
  3. Scope: does it allow this tool?
  4. Expiry: is it still alive?
  5. Case: is this record part of the token's case?

Checkpoint

Which check was missing?

Mukhallis holds a token with audience case-server and scope case:read. A changed tool sends that token to the comms server, which checks the signature and expiry, finds them valid, and sends an email. Which check did the comms server skip?

That the token's audience is the comms server itself
That the token was issued within the last two minutes
That the officer named in the token is on duty
That the scope contains the word "read"
Why. A token is good only at the audience it was issued for. A server that accepts tokens meant for another server is open to replay.

Answer: the first. This is the second line of the deputy test in the lab.

04

Session 4: the last control of the day changes the architecture. The model that reads untrusted text loses its tools.

Privileged and quarantined

Split the model's work by what each call may touch

Quarantined callPrivileged call
ReadsThe raw email and invoiceTyped fields, system records
ToolsNoneAll of them
If fooledReturns wrong fieldsIt is not shown the attacker's text
In MukhallisThe extraction of invoice fieldsThe planner

The dual LLM pattern, proposed by Simon Willison in 2023; CaMeL and the design-patterns paper of 2025 develop it. This is where Day 1's distinction returns: the quarantined call is the model as a component. Sources: Willison, The Dual LLM pattern; Debenedetti and others, CaMeL; Beurer-Kellner and others, Design Patterns for Securing LLM Agents.

Typed fields

Only values that pass a check cross, and a failed field becomes empty, not repaired

FieldCheckA failing value becomes
hs_codeFour digits, a dot, two digitsNone
valueA number, positiveNone
currencyOne of five listed codesNone
originTwo capital lettersNone
notesRemovedNot passed
Not repaired. A check that "cleans" a field is a second parser for the attacker to study. Refuse, and let the officer see the empty field.

The lab's checks: no free text crosses, the value is a number, a failing field becomes None, and nothing instruction-like is left in what the planner sees. Day 4 generalises this to every tool argument.

Checkpoint

Why do attacks still cross?

A team splits its agent: one call reads supplier emails and returns JSON, a second call with tools plans from that JSON. Attacks still succeed half the time. The JSON has a field comments with free text from the email. What is the flaw?

The first call should have had the tools, not the second
JSON is not a safe format between two calls
Free text crosses the split, so the planner still reads the attacker's words
The second call needs a stronger system prompt
Why. The split works only when what crosses is typed and checked. One free-text field undoes it.

Answer: the third. Ask what to do when the officer needs the importer's comments: show them to the officer on the screen, escaped, and never to the planner.

Day 3 · wrap-up

Three things to keep

Contain, do not persuade

Four controls, and none asked anything of the model. Their zeros are exact.

Two numbers, every time

Attacks stopped and benign tasks passing. A first rule usually fails the second number.

Authority travels with the call

One audience, one scope, one case, two minutes. The server checks, not the agent.
